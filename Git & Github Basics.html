Module 01 · Core Foundations

Git vs GitHub: Version Control Principles

Git is a distributed Version Control System (VCS) created by Linus Torvalds, the creator of the Linux kernel. Unlike short-lived developer tools, Git has remained foundational across software careers because it solves a permanent problem: tracking every change made to files—what changed, when it changed, who changed it, and which line was modified—24 hours a day, 365 days a year.

Crucially, Git is not restricted to source code. While it is ubiquitous in JavaScript, PHP, Python, and systems programming, it can track and preserve multiple versions of text documents, configuration files, images, and even video assets.

Real-World Scenario: Why Version Control Saves Projects

Suppose you spend weeks building a client project. The client approves Version 1. A month later, they ask for substantial new features, so you overwrite the original files to build Version 2. Days later, the client says: “Actually, the earlier version was better.” Without version control, your original work is gone. With Git, every historical version remains safely indexed, letting you roll back to any prior state in seconds.

The Coffee & Coffee Shop Analogy

Beginners frequently conflate Git and GitHub. Although they work together, they serve entirely different roles:

Local Engine

Git is the Coffee

Git is the tool installed and executed locally on your own computer. It records file snapshots, tracks line-by-line history, manages branches, and operates entirely offline without needing an internet connection.

Cloud Collaboration Hub

GitHub is the Coffee Shop

GitHub (owned by Microsoft) is the central cloud server where that coffee is served. When multiple teammates edit the same project on separate computers, GitHub acts as the single shared hub where everyone uploads, reviews, and merges their updates.

Git Hosting Platforms Compared

GitHub is the most widely adopted platform—especially across open-source ecosystems—but Git itself is platform-agnostic. Other trusted remote hosts include GitLab and Bitbucket.

Platform Primary Strength Typical Ecosystem
GitHub Largest open-source community, Pull Requests, GitHub Actions, Microsoft-backed Open source, startups, enterprise teams
GitLab Built-in end-to-end DevSecOps pipelines and self-hosting options Enterprise DevOps & self-managed infrastructure
Bitbucket Tight integration with Jira and Confluence (Atlassian suite) Teams already running Atlassian tooling
Module 02 · Internal Architecture

The Four Stages of Git’s Workflow

Every Git command makes sense once you map it onto Git’s two-part architecture—Local (on your computer) and Remote (in the cloud)—split across four distinct stages:

Stage 01 · Local

Working Directory

Your active project folder on disk (e.g., git-1). Here you create new files, write code, modify existing files, or delete obsolete ones. Git observes changes here, but nothing is saved to history yet.

Stage 02 · Local

Staging Area (Index)

An intermediate holding zone between your workspace and permanent history. Moving files here with git add signals: “These specific changes are ready for the next snapshot.”

Stage 03 · Local

Local Repository

A hidden digital cabinet (.git/) on your computer. Running git commit permanently locks staged snapshots into your project’s local timeline.

Stage 04 · Cloud

Remote Repository

A cloud-hosted mirror on GitHub, GitLab, or Bitbucket—much like Google Drive or OneDrive for code. You git push commits here for backup, multi-device access, and team collaboration.

Module 03 · Environment & Identity

Installation, Terminal Navigation & User Config

Installing Git Across Operating Systems

Download the official installer from git-scm.com (search for the official Git downloads page) for your operating system:

Operating System Installation Method Recommended Terminal
Windows Choose the 32-bit or 64-bit setup installer and follow the wizard. Command Prompt, PowerShell, or Git Bash (bundled with Git; mimics a Linux shell for intuitive commands).
macOS Follow the official Homebrew instruction: brew install git. Built-in Terminal app (or iTerm2).
Linux / Unix Install via your distribution’s package manager (e.g., apt, dnf) per the official guide. System terminal shell (Bash / Zsh).

Confirm your installation works by running:

git --version
# Example output: git version 2.45.0

Essential Non-Git Terminal Commands

Before running Git commands, you navigate folders using standard shell utilities (these are operating system commands, not Git commands):

  • pwd — Print working directory (shows your current folder path).
  • cd Desktop — Change directory into Desktop; cd ../ or cd .. moves one level up.
  • mkdir git-1 — Create a new directory named git-1.
  • touch 1.txt — Create an empty file named 1.txt (on Windows PowerShell, use New-Item 1.txt or Git Bash’s touch).
  • ls and ls -la — List files; -la reveals hidden system directories such as .git.
  • open . — Open the current directory (.) in macOS Finder (on Windows Git Bash, use explorer .).

Configuring Your Git Identity (Global vs Local)

The very first time you attempt a commit on a fresh installation, Git pauses and prints: Please tell me who you are. Because Git records the author on every commit in the project history, you must register a name and email address first: 

# Apply to EVERY repository on your computer (--global)
git config --global user.name "Sumit Saha"
git config --global user.email "sumit@example.com"

# OR apply ONLY to the current project repository (--local)
git config --local user.name "Work Profile"
git config --local user.email "work@company.example"

Use --global for your personal machine default, and override with --local inside specific repositories when separating personal open-source commits from corporate accounts.

Module 04 · Repositories & Tracking

git init, git clone & the Hidden .git Folder

Two Ways to Start a Git Repository

Whether starting locally on your hard drive or pulling an existing project down from GitHub, initialisation is mandatory before Git can track changes:

Approach A · Local First

git init

Navigate into your project folder (e.g., git-1 containing 1.txt, 2.txt, and my-folder/3.txt) and run git init. Terminal prints: “Initialized empty Git repository.”

Running ls -la reveals a hidden .git/ folder—Git’s internal database storing all file versions, commit metadata, authors, and branch pointers.

Approach B · Cloud First

git clone <https-url>

Create a repository on GitHub (e.g., git-journey, set to Public, add 1.txt and 2.txt via “Create a new file” and “Commit changes”). Click the Code button, copy the HTTPS link, and run git clone <url>.

Git creates the git-journey/ directory locally, downloads all files, and automatically includes a complete .git/ repository linked to origin.

Inspecting Live Changes with git status

Whenever you edit 1.txt or 2.txt, or create a brand-new folder my-folder/ containing 3.txt, running git status gives an immediate project summary:

  • Modified (tracked): Files Git already knew about from previous commits (e.g., modified: 1.txt).
  • Untracked: Newly created files or folders that Git has never committed before (e.g., my-folder/).
  • Clean working tree: When all local edits match the latest commit.
Module 05 · Staging & Commits

git add Variations, Commits & Rolling Back

The Party-Preparation Mirror Analogy

Why doesn’t Git save straight from your working directory into the repository? Think of getting dressed for a party. You do not walk straight out of the front door; you pause in front of a mirror to check your shirt, shoes, hair, and tie. If something looks wrong, you adjust it right there.

The staging area is that mirror. git add lets you review, adjust, or unstage (git reset) specific changes before locking them permanently into history with git commit.

Every git add Variation Explained

Subtle flags on git add behave differently depending on your current folder and whether files were deleted:

Interactive Explorer 02

Compare git add Flag Scopes

Scenario: 1.txt modified, 2.txt deleted, 4.txt new (root), my-folder/3.txt new
Command Scope New & Modified Deleted Files
git add --all / git add -A Entire repository (even if run from a subfolder) Staged Staged
git add . Current working folder and its subdirectories only Staged Staged
git add * Current directory shell glob (skips dotfiles) Staged Ignored (not staged)
git add 1.txt / my-folder/3.txt Single named file path only Staged Staged if named
git add *.txt Matching .txt files in current root folder only Staged Ignored

Unstaging, Committing & Undoing the Last Commit

# Unstage all files back to the working directory (keeps your file edits safe)
git reset

# Permanently commit staged changes with a clear message
git commit -m "Add user profile validation and update 1.txt"

# Undo the most recent commit and return its changes to the working directory
git reset HEAD~
Commit Message Best Practices

Write commit messages in the imperative mood (e.g., “Add dark mode toggle” rather than “Added stuff”), keep each commit focused on a single logical change (atomic commits), and ensure the summary clearly explains why the snapshot exists when browsing git log months later.

Module 06 · File Removal & History Inspection

git rm, Hard Resets, Logs & git diff

File Deletion & Untracking with git rm

Manually deleting a file in Finder/Explorer requires a second git add . step to stage the deletion. git rm performs both actions together—and provides flags for special cases:

  • git rm 4.txt — Deletes 4.txt from disk and immediately stages the deletion for the next commit.
  • git rm -f 4.txt — Force-deletes even if Git warns “the following file has local modifications” (uncommitted edits in the working directory).
  • git rm --cached 4.txt — Removes the file from Git’s tracking/staging index while keeping the physical file intact on your hard drive as an untracked file (essential when you accidentally tracked a secret .env file).
  • git rm -r my-folder — Recursively deletes a folder and all subfolders/files inside it, staging the removal.
git reset vs git reset --hard After Deletion

Running plain git reset unstages changes, but it does not bring back files deleted from your file system. To discard uncommitted changes and physically restore deleted files to their last committed state, run git reset --hard.

Inspecting Commits & Reading Diffs

# Full commit history (long 40-character SHA hashes, author, date, full message)
git log

# Compact one-line summary with shortened commit IDs
git log --oneline

# Exit the terminal pager when viewing long logs
# Press the 'q' key on your keyboard

# Compare two commits (newer commit first, older commit second)
git diff <newer-commit-id> <older-commit-id>

In git diff, placing the newer commit ID first displays additions in green (+) and removals in red (-) from the newer snapshot’s perspective. Reversing the IDs flips the perspective.

Module 07 · Parallel Development

Branching, Merging & Resolving Conflicts

Every repository starts with a primary line of development—historically called master, now standardly named main. A branch is an independent, isolated line of development forked from a snapshot of your project.

The Restaurant Kitchen Analogy

Think of main as the restaurant’s live service kitchen preparing meals for paying guests. When a client asks for an experimental recipe, you never test it in the main kitchen—one mistake ruins service. Instead, you open a separate test kitchen (a development or feature branch), perfect and taste the dish safely, and only merge it back into the main kitchen once verified.

Branching & Switching Commands

# List all local branches (* marks your active branch)
git branch

# Create a new branch inheriting the current branch's state
git branch development

# Switch to a branch (classic command vs modern Git 2.23+ command)
git checkout development
git switch development

# Create and switch in one step
git checkout -b staging
git switch -c staging

When you create and commit 3.txt inside development and switch back to main, 3.txt vanishes from your file explorer immediately—and reappears when you switch back to development. Git seamlessly rewrites your working tree to show only the commits belonging to the active branch (provided your changes were committed first).

Merging & Resolving Merge Conflicts

To combine completed work from development into main, switch to the receiving branch and merge: 

git checkout main
git merge development -m "Merging main with development"

A merge conflict arises when two branches edit the exact same line(s) of the same file differently—for example, staging appends 44 to 4.txt while development appends 444 on the same line. Git stops with Automatic merge failed; fix conflicts and then commit the result and writes conflict markers into the file.

Recommended Branching Strategies

  • Feature Branching: Keep main always deployable; fork short-lived branches like feature/auth or fix/header and merge via Pull Requests.
  • Main + Staging + Development: Integrate daily work in development, promote release candidates to staging for QA testing, and merge verified releases into main.
Module 08 · History Navigation

Time Travel & Detached HEAD State

Just as git checkout <branch> moves between branches, passing a specific commit hash lets you travel backwards in time to inspect your project exactly as it stood at that moment: 

# 1. Locate the target commit ID
git log --oneline

# 2. Check out that exact snapshot (ensure working tree is clean first)
git checkout a1b2c3d

# Terminal warns: "You are in 'detached HEAD' state."
# 3. Return to the latest tip of main when finished inspecting
git checkout main

Normally, Git’s HEAD pointer points to a branch name (like main), which moves forward automatically when you commit. In detached HEAD state, HEAD points directly to a historical commit instead of a branch. Inspecting files is completely safe, but if you want to keep any new commits made while detached, create a branch first with git checkout -b rescue-branch before returning to main.

Module 09 · Remote Synchronisation

git push, git fetch & git pull

Once commits are recorded locally, three commands handle daily synchronisation between your local repository and GitHub (conventionally named origin; inspect with git remote -v):

Local → Cloud

git push origin <branch>

Uploads commits from your local branch to the remote repository. Pushing main only uploads main; you push staging or development separately to create and sync them on GitHub.

Cloud → Local Repo Only

git fetch

Downloads new remote commits into local repository memory so you can inspect incoming updates safely, without modifying your working directory files until you run git merge.

Cloud → Working Directory

git pull

Combines both operations in one command: git pull = git fetch + git merge. Remote updates immediately appear in your local working files.

Module 10 · Undoing & Safety Nets

git restore, git stash & git revert vs git reset

Discarding Local Mistakes with git restore

Suppose you modified 10–15 files while prototyping an idea that fails, and you want to revert them cleanly to the last commit without manually editing each file:

  • git restore 1.txt — Discards uncommitted working-directory edits in 1.txt.
  • git restore . or git restore <dir> — Restores all files in the directory/repo to the last committed snapshot.
  • git restore --staged 1.txt (or --staged .) — Removes files from the staging area while preserving your edits in the working directory.

Shelving Half-Finished Work with git stash

If you are halfway through an uncommitted feature on main and try to switch branches, Git blocks you: “Your local changes to the following files would be overwritten by checkout.” Instead of discarding your progress or making a broken commit, use the stash stack:

git revert vs git reset (The Oversalted Dish Analogy)

Imagine accidentally adding too much salt while cooking. You do not throw the entire pot out (erasing history); instead, you balance the dish by adding complementary ingredients.

Dimension git reset (e.g., HEAD~ / --hard) git revert <commit-id>
How it undoes Moves the branch pointer backwards and deletes subsequent commits from the log. Creates a brand-new commit that applies the exact inverse changes of the faulty commit.
History record Erases evidence that the removed commits ever happened. Preserves full audit history (Revert "hello 3", saved via :wq in editor).
Safe on shared GitHub branches? No — causes divergence errors for teammates. Yes — non-destructive and safe for collaborative branches.

Module 11 · History Management

git rebase vs git merge & the Golden Rule

When your feature branch falls behind new production updates on main, running git merge main brings those updates in—but creates an extra merge commit every time, cluttering git log. git rebase main solves this by rewriting your feature branch onto the latest tip of main.

How git rebase Works Internally (4 Steps)

  1. Git locates the most recent common ancestor commit shared between feature and main.
  2. Git temporarily sets aside all commits unique to feature.
  3. Git fast-forwards feature to include every new commit from main.
  4. Git replays your saved feature commits one by one on top—creating new commit IDs and a clean linear history.
Interactive Visualiser 05

Commit Graph: git merge main vs git rebase main

The Golden Rule of Rebasing

Never run git rebase on public or shared remote branches where other developers are actively committing. Because rebase rewrites commit history and alters commit IDs, collaborators’ local copies will no longer match the rewritten history, breaking normal git pull syncs. Use rebase freely on your personal local feature branches before sharing.

Module 12 · Team Code Review

Pull Requests (PRs) on GitHub

In team repositories, developers do not push changes directly into main. Instead, a Pull Request (PR) formally asks maintainers to inspect your branch, discuss changes, and merge them safely once approved.

Step-by-Step Pull Request Workflow

  1. Push your feature or development branch to GitHub (git push origin development).
  2. Open the repository on GitHub, select the Pull requests tab, and click New pull request.
  3. Set the two dropdowns carefully: Base = destination branch (main) and Compare = source branch containing your updates (development).
  4. Inspect the live diff preview, click Create pull request, enter a clear title (e.g., “Merge development updates into main”) and description, then submit.
  5. Review across GitHub’s three PR tabs:
    • Conversation: Team discussion, review comments, and automated checks.
    • Commits: Complete list of individual commits included in the PR.
    • Files changed: Line-by-line additions and deletions across modified files.
  6. Once approved, click Merge pull request → Confirm merge. GitHub displays: “Pull request successfully merged and closed.”

Module 14 · Practical Extras

Troubleshooting Common Git Gotchas

Quick diagnoses and exact fixes for the most frequent errors encountered by learners and working teams:

Error: “Please tell me who you are” when running git commit

Cause: Git has no configured author name or email on this machine/repo yet.

Fix: Run git config --global user.name "Your Name" and git config --global user.email "you@example.com" (or use --local for one repo only), then re-run your commit.

Trapped inside the terminal after running git log or git revert

Cause: Long logs open in the terminal pager (less), while git revert opens the default text editor (often Vim) for the revert commit message.

Fix: Press q to exit the log pager. Inside Vim during a revert, press Esc, type :wq (write and quit), and press Enter.

Added a file to .gitignore, yet Git keeps tracking its changes

Cause: .gitignore only ignores untracked files. Once a file (such as .env) has been committed, Git continues tracking it.

Fix: Run git rm --cached .env (or git rm -r --cached node_modules) to untrack it without deleting it from disk, then commit the removal.

Error: “Your local changes to the following files would be overwritten by checkout”

Cause: You have uncommitted local edits in a file that differs on the target branch.

Fix: Run git stash to shelter your uncommitted edits, switch branches, and later restore them with git stash pop.

Accidentally committed work while in Detached HEAD state

Cause: Checking out a commit ID instead of a branch leaves HEAD unattached; switching back to main would leave new commits orphaned.

Fix: Immediately run git checkout -b saved-work before leaving detached state so a named branch preserves your commits.
